# Security policy

## Reporting a vulnerability

After the public GitHub cutover, use the repository's **Report a vulnerability** action
to submit a private vulnerability report. Do not disclose suspected vulnerabilities in
public issues, pull requests, discussions, logs, or example repositories.

Include the affected version, impact, reproduction steps, and the smallest evidence
needed to investigate. Do not include real credentials, unrelated repository content,
or personal data. If private vulnerability reporting is not available, do not publish
the report; wait for the repository owner to enable the approved private channel.

Reports and fixes are handled on a best-effort basis with no response or remediation
service-level agreement. The maintainer may coordinate an embargoed fix through a draft
GitHub security advisory and request a CVE when warranted. An authorized human controls
disclosure, merge, tagging, and publication.

## Supported versions

Before 1.0, only the current development version is considered for best-effort security
fixes. After 1.0, only the latest public 1.x release is supported unless a maintenance
branch is explicitly announced. A defective but intact public release is normally
yanked with a reason and repaired by a new version; published versions and filenames are
never reused.
